The project goal

The objective was not simply to display Pokémon cards. I wanted to demonstrate a maintainable way to fetch, cache and present remote data in a modern React application.

The application retrieves a Pokémon list from PokéAPI, requests the detailed record for each item, and then renders a searchable catalogue. Users can search by Pokémon name or Pokédex number and immediately see matching results.

Core engineering question: how can the UI remain simple while request status, cached data and API errors are handled consistently?

Architecture and data flow

I separated the application into three responsibilities: the RTK Query API service owns remote data, the Redux store integrates that service, and React components focus on presentation and interaction.

1 · RequestThe component calls the generated query hook.
2 · CacheRTK Query fetches data and stores the result.
3 · RenderReact responds to loading, error and success states.

This structure avoids scattering fetch logic and duplicated request state across components. It also gives the application a single, predictable data pipeline.

Creating the RTK Query API layer

The API service uses createApi and fetchBaseQuery. A custom queryFn first loads the list and then uses Promise.all to resolve the detailed endpoints.

export const pokemonApi = createApi({
  reducerPath: "pokemonApi",
  baseQuery: fetchBaseQuery({
    baseUrl: "https://pokeapi.co/api/v2/"
  }),
  endpoints: (builder) => ({
    getPokemon: builder.query({
      async queryFn(_, api, options, baseQuery) {
        const list = await baseQuery("pokemon?limit=124");
        if (list.error) return { error: list.error };

        const details = await Promise.all(
          list.data.results.map(({ name }) =>
            baseQuery(`pokemon/${name}`)
          )
        );

        const failed = details.find(item => item.error);
        if (failed) return { error: failed.error };
        return { data: details.map(item => item.data) };
      }
    })
  })
});

RTK Query generates the React hook automatically. The component receives data, isLoading and error without maintaining separate request reducers or action creators.

Building the catalogue and search

The interface is component-driven: a list component coordinates data and filtering, while each card displays the individual Pokémon information. Search is performed on the already-fetched client data, so the results update immediately without an additional request.

  • Controlled input keeps the search term synchronized with React state.
  • Normalization makes name matching case-insensitive.
  • Number matching lets users search by Pokédex ID.
  • Reusable cards keep presentation logic isolated from data orchestration.

Designing for loading, failure and success

Network-backed interfaces are never only their successful result. The UI explicitly accounts for loading and request failures before attempting to render the grid. This prevents undefined-data errors and gives users clear feedback while PokéAPI responds.

The API layer also checks both the initial list request and every detailed request. If one of them fails, it returns an RTK Query-compatible error instead of partially pretending the operation succeeded.

Performance considerations

The current implementation intentionally loads a bounded set of 124 Pokémon. Concurrent detail requests reduce total waiting time, and RTK Query prevents the same mounted query from being fetched repeatedly without reason.

For a much larger production catalogue, I would evolve this design with pagination or lazy loading, controlled concurrency for detail requests, and cache lifetime settings matched to how frequently the source data changes.

From local development to deployment

Vite provides the development and production build pipeline. The production command generates optimized static assets in the dist directory. Those assets are deployed as a separate free static site on Render.

The deployment is isolated from my other applications, connected only to this repository, and configured to rebuild automatically when changes reach the main branch. Because the browser communicates directly with the public PokéAPI, this project does not require a paid application server or database.

What this project reinforced

  • Server state deserves a dedicated abstraction rather than ad hoc fetching in components.
  • Generated hooks can reduce boilerplate without hiding important request states.
  • Clear component boundaries make UI features such as filtering easier to extend.
  • Error handling should cover every request in a multi-request workflow.
  • A static React application can still demonstrate meaningful architecture and production delivery.
